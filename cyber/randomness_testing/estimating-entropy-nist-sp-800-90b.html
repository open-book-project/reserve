    Chapter 5: Estimating Entropy: NIST SP 800-90B¶

    SP 800-22 asks whether data looks random. SP 800-90B asks a different and more useful question for cryptography: how many bits of guessing work does each sample of a noise source give an attacker? Its answer is a number, the min-entropy per sample, produced by a family of estimators and made into a continuous safeguard by two health tests that run inside the device. This chapter works through the estimators one at a time, then the restart tests, then the repetition count and adaptive proportion tests.

    5.1 The question SP 800-90B asks¶

    This one asks a different question. SP 800-22 asks "does this look random?", while SP 800-90B (Turan and colleagues, January 2018) asks "how many bits of guessing work does each sample give an attacker?". It was written for the noise sources inside entropy sources, and it is used in NIST's Cryptographic Algorithm Validation Program (CAVP) and Cryptographic Module Validation Program (CMVP). You supply at least 1,000,000 consecutive raw samples, plus a restart matrix of 1000 samples from each of 1000 restarts. You also state your own expected entropy from a design analysis. Data then follows one of two tracks. The IID track is open only if you claim independent, identically distributed (i.i.d.) samples and the tests below find nothing against that. Everything else follows the non-IID track. The output is not a p-value but a number: bits of min-entropy per sample. Taking the smallest estimate is deliberate, because we want the most cautious answer. NIST also warns that these estimators support an analysis of the source and do not replace it.

    5.2 Min-entropy framing¶

    The idea in plain words. Imagine an attacker with one guess. Their best move is to bet on the most likely value. Min-entropy measures exactly how hard that one bet is, so it is set by the single most likely outcome and nothing else. That is why it is cautious: a distribution can look rich on average and still have one value an attacker will always try first.

    Example 5.2: Min-entropy framing

    Suppose three values have probabilities 0.5, 0.25, 0.25. The min-entropy is \(-\log_2 0.5 = 1\) bit, while the Shannon entropy is 1.5 bits. A bit that comes up 1 sixty percent of the time has min-entropy \(-\log_2 0.6 = 0.737\) bits.

    The mathematics.

    \[H = \min_{1 \le i \le k} \left(-\log_2 p_i\right) = -\log_2 \max_{1 \le i \le k} p_i\]
    \[H_I = \min\!\left(H_{original},\ n \cdot H_{bitstring},\ H_{submitter}\right)\]
    • \(p_i\) is the probability of value \(x_i\), and \(k\) is the number of possible values, so \(H\) is at most \(\log_2 k\).
    • \(H_{original}\) is estimated on the samples, \(H_{bitstring}\) on the same data read as a bit string, and \(n\) is the number of bits per sample.
    • \(H_{submitter}\) is your own design-based claim. For a binary source, \(H_I\) uses only \(H_{original}\) and \(H_{submitter}\).

    What it catches and misses. This framing puts the attacker's best guess at the centre, which suits cryptography. It still only measures what the estimators can spot. A cleverly deterministic source can score high, which is why a design rationale is required.

    5.3 Permutation tests (IID track)¶

    The idea in plain words. Take the data, shuffle it, and measure something. Shuffling destroys any order but keeps the mix of values. If the data really is i.i.d., the original should look like just another shuffle. If its score sits at the extreme end of 10,000 shuffles, then order mattered, and the data is not i.i.d. It is like asking whether a dealt hand looks any different from one dealt after a good shuffle.

    Example 5.3: Permutation tests (IID track)

    The excursion statistic on \(S = (2, 15, 4, 10, 9)\) has mean 8, giving deviations 6, 1, 3, 1, 0, so \(T = 6\). For \(S = (2, 2, 2, 5, 7, 7, 9, 3, 1, 4, 4)\) the steps are six ups, two downs, then two ups. That gives 3 directional runs, a longest run of 6, and 8 increases.

    The mathematics.

    \[\text{reject i.i.d. if } C_{i,0} + C_{i,1} \le 5 \quad \text{or} \quad C_{i,0} \ge 9995\]
    • \(T_i\) is statistic \(i\) on the original data, and each of the 10,000 shuffles uses the Fisher-Yates algorithm, a standard shuffle that makes every ordering equally likely.
    • \(C_{i,0}\) counts shuffles with a larger statistic, and \(C_{i,1}\) counts ties.
    • The cutoffs correspond to a type I error (rejecting good data, a false alarm) of 0.001.

    The statistics are: excursion, number of directional runs, length of directional runs, number of increases and decreases, number of runs about the median, length of runs about the median, average collision, maximum collision, periodicity and covariance (each at lags 1, 2, 8, 16 and 32), and compressed length under bzip2. Some are applied to binary data after grouping it into 8-bit blocks.

    What it catches and misses. The reference distribution comes from the data itself, so no theory is assumed. It catches trends, repeats and lagged relations in the listed statistics. It cannot reject a source that is i.i.d. but heavily biased, because bias survives shuffling. That is a job for the estimators.

    5.4 Chi-square tests (IID track)¶

    The idea in plain words. Two more checks back up the shuffling. The independence test asks whether a value's neighbour tells you anything about it, by comparing pair counts with what the individual frequencies predict. The goodness-of-fit test asks whether ten slices of the data all share the same distribution, like checking that a factory's output does not change from shift to shift.

    Example 5.4: Chi-square tests (IID track)

    The standard's non-binary example has \(k = 3\) values, \(L = 100\) and proportions 0.21, 0.41, 0.38. With six bins, the observed counts are 7, 6, 10, 8, 12, 7 against expected 6.2, 8.3, 11.53, 7.79, 7.79, 8.41. So \(T = 3.46\) with 3 degrees of freedom, far below the critical value 16.266, and the test passes.

    The mathematics.

    \[T = \sum_{\text{bins}} \frac{(o_i - e_i)^2}{e_i}\]
    Test Data Expected count Degrees of freedom
    Independence non-binary \(p_i p_j L/2\) for non-overlapping pairs, binned so each bin expects at least 5 \(n_{bin} - k\)
    Goodness of fit non-binary \(c_i/10\) for each of ten subsets, binned the same way \(9(n_{bin} - 1)\)
    Independence binary \(p_1^w p_0^{m-w}\lfloor L/m \rfloor\) for each \(m\)-bit tuple with \(w\) ones, \(m\) at most 11 \(2^m - 2\)
    Goodness of fit binary \((1-p)L/10\) zeros and \(pL/10\) ones in each of ten subsets 9
    • \(o_i\) and \(e_i\) are observed and expected counts, and \(k\) is the alphabet size.
    • \(p_i\) is the proportion of value \(x_i\), and \(c_i\) is its count.
    • Each test fails if \(T\) exceeds the chi-square critical value at 0.001. The document prints that value for 9 degrees of freedom as 27.887, while chi-square tables give 27.877.

    What it catches and misses. Independence catches dependence in adjacent samples or nearby bits, and goodness of fit catches drift over the run. Dependence at longer lag is out of reach here, so it relies on the permutation tests.

    5.5 Longest repeated substring test (IID track)¶

    The idea in plain words. In random data, long repeated stretches are rare, and we can calculate how rare. Find the longest stretch that occurs twice and ask how likely a repeat that long would be if the samples were i.i.d. It is like finding the same long sentence in two parts of a book: past a certain length, chance stops being a good explanation.

    Example 5.5: Longest repeated substring test (IID track)

    For \(S = (2, 2, 0, 1, 0, 2, 0, 1, 2, 1, 2, 0, 1, 2, 1, 0, 0, 1, 0, 0, 0)\) we have \(L = 21\), \(p_{col} = 0.3469\) and longest repeat \(W = 5\). That gives \(N = 136\) pairs and \(\Pr(X \ge 1) = 0.496\), comfortably above 0.001, so it passes.

    The mathematics.

    \[p_{col} = \sum_{i=1}^{k} p_i^2, \qquad N = \binom{L-W+1}{2}, \qquad \Pr(X \ge 1) = 1 - \left(1 - p_{col}^{\,W}\right)^N\]
    • \(p_i\) is the proportion of value \(x_i\), and \(L\) is the sample count.
    • \(W\) is the length of the longest repeated substring.
    • \(X\) is binomial with \(N\) trials and success probability \(p_{col}^{\,W}\).

    The test fails if \(\Pr(X \ge 1) < 0.001\).

    What it catches and misses. It catches long repeats, such as a source that loops or replays stored data, and it works on binary and non-binary input alike. It uses only the longest repeat, so a source full of medium-length repeats may slip through.

    5.6 Most common value estimate¶

    The idea in plain words. Find the most frequent value, then allow for sampling luck by taking the top of a 99 percent confidence interval. It is the simplest estimate of all, often shortened to MCV: the attacker's single best guess, treated cautiously. On the IID track, this is the only estimator used.

    Example 5.6: Most common value estimate

    For \(S = (0, 1, 1, 2, 0, 1, 2, 2, 0, 1, 0, 1, 1, 0, 2, 2, 1, 0, 2, 1)\), \(L = 20\) and the value 1 appears 8 times, so \(\hat{p} = 0.4\). Then \(p_u = 0.4 + 2.576\sqrt{0.24/19} = 0.6895\) and the estimate is \(-\log_2 0.6895 = 0.5363\) bits. The document prints 0.6822 inside its logarithm, but 0.5363 only follows from 0.6895.

    The mathematics.

    \[\hat{p} = \max_i \frac{\#\{x_i \text{ in } S\}}{L}, \qquad p_u = \min\!\left(1,\ \hat{p} + 2.576\sqrt{\frac{\hat{p}(1-\hat{p})}{L-1}}\right), \qquad H = -\log_2 p_u\]
    • \(L\) is the number of samples.
    • 2.576 is the normal quantile \(Z_{(1-0.005)}\).

    What it catches and misses. It catches bias well. On its own it is blind to dependence: a stream alternating 0, 1, 0, 1 has \(\hat{p}\) near 0.5 and scores nearly a full bit per sample. NIST warns that it typically overestimates entropy when samples are not i.i.d.

    5.7 Collision estimate¶

    The idea in plain words. Read the stream until you see a value you have already seen, then start again. If one value dominates, repeats come quickly. So the average time to a repeat tells you about the most likely value, much like the birthday puzzle in reverse. This estimator is applied to binary input only.

    Example 5.7: Collision estimate

    The standard's 40-bit example gives times 3, 3, 3, 3, 3, 2, 3, 2, 2, 3, 3, 3, 3, 2, so \(v = 14\), \(\bar{X} = 2.7143\) and \(\hat{\sigma} = 0.4688\). The lower bound is \(\bar{X}' = 2.3915\). Solving gives \(p = 0.7329\) and an estimate of 0.4483 bits.

    The mathematics.

    \[\bar{X}' = \bar{X} - 2.576\frac{\hat{\sigma}}{\sqrt{v}}, \qquad \bar{X}' = pq^{-2}\left(1 + \tfrac{1}{2}(p^{-1} - q^{-1})\right)F(q) - pq^{-1}\,\tfrac{1}{2}(p^{-1} - q^{-1})\]
    • \(t_i\) are the times to a repeat, with mean \(\bar{X}\) and standard deviation \(\hat{\sigma}\) across \(v\) repeats.
    • \(q = 1 - p\) with \(p \ge q\), and \(F(1/z) = \Gamma(3, z)z^{-3}e^z\), using the incomplete gamma function.
    • \(p\) is found by binary search between \(1/2\) and 1, and the estimate is \(-\log_2 p\), or 1 if there is no solution.

    For bits, the right-hand side works out to \(2 + 2pq\), which we checked against the standard's example.

    What it catches and misses. It catches considerable bias towards one value. In bits, a repeat comes after two or three steps, so the measure is coarse. It sees only nearby repeats and cannot read longer-term structure.

    5.8 Markov estimate¶

    The idea in plain words. Suppose each bit depends only on the one before it. We measure the four transition chances from the data, then ask which 128-bit sequence is most likely and how likely it is. Dividing by 128 gives entropy per bit. Think of predicting tomorrow's weather from today's alone.

    Example 5.8: Markov estimate

    The standard's 40-bit example gives \(P_0 = 0.475\), \(P_1 = 0.525\), \(P_{0,0} = 0.389\), \(P_{0,1} = 0.611\), \(P_{1,0} = 0.571\) and \(P_{1,1} = 0.429\). The likeliest path is 1010...10, with probability about \(4.6288 \times 10^{-30}\) on those rounded inputs. So the estimate is \(\min(-\log_2(4.6288 \times 10^{-30})/128, 1) = 0.761\) bits.

    The mathematics.

    \[\hat{p}_{max} = \max\left\{P_0 P_{0,0}^{127},\ P_0 P_{0,1}^{64} P_{1,0}^{63},\ P_0 P_{0,1} P_{1,1}^{126},\ P_1 P_{1,0} P_{0,0}^{126},\ P_1 P_{1,0}^{64} P_{0,1}^{63},\ P_1 P_{1,1}^{127}\right\}\]
    \[H = \min\!\left(-\frac{\log_2 \hat{p}_{max}}{128},\ 1\right)\]
    • \(P_0\) and \(P_1\) are the proportions of zeros and ones.
    • \(P_{a,b}\) is the observed chance that bit \(a\) is followed by bit \(b\).

    This is applied to binary input only. NIST notes that the per-sample extrapolation from a 128-long chain is not strictly correct but is close in practice.

    What it catches and misses. It catches first-order dependence such as a stickiness or a tendency to alternate. It assumes a one-step memory, so it does not model dependence two or more steps back.

    5.9 Compression estimate¶

    The idea in plain words. This uses Maurer's idea from SP 800-22 in a new way. Warm up a dictionary, then measure how far back each block last appeared. Then find the most skewed distribution that would produce an average that small, and read off its entropy. In effect, we ask how compressible the data is, then assume the worst source consistent with that.

    Example 5.9: Compression estimate

    The standard's illustration uses \(d = 4\), \(L = 48\) and \(b = 6\), with test blocks at distances \(D = (5, 6, 7, 7)\). So \(\bar{X} = 2.6304\), \(\hat{\sigma} = 0.9074\) and \(\bar{X}' = 1.4617\). Solving gives \(p = 0.5715\) and \(H = -\log_2(0.5715)/6 = 0.1345\) bits.

    The mathematics.

    \[\bar{X} = \frac{1}{v}\sum_{i=1}^{v} \log_2 D_i, \qquad \hat{\sigma} = c\sqrt{\frac{\sum_i (\log_2 D_i)^2}{v-1} - \bar{X}^2}, \qquad \bar{X}' = \bar{X} - 2.576\frac{\hat{\sigma}}{\sqrt{v}}\]
    \[\bar{X}' = G(p) + (2^b - 1)G(q), \qquad G(z) = \frac{1}{v}\sum_{t=d+1}^{\lfloor L/b \rfloor}\sum_{u=1}^{t} \log_2(u)\,F(z,t,u)\]
    • \(b = 6\) is the block size, \(d = 1000\) the dictionary size, and \(c = 0.5907\) the correction factor.
    • \(q = (1-p)/(2^b - 1)\), and \(F(z,t,u) = z^2(1-z)^{u-1}\) if \(u < t\) and \(z(1-z)^{t-1}\) if \(u = t\).
    • \(p\) is searched between \(2^{-b}\) and 1, and \(H = -\log_2(p)/b\), or 1 if no solution exists.

    What it catches and misses. It assumes no independence, so dependence does show through. It catches repeats at the 6-bit level. It reasons about a near-uniform worst case, and it is applied only to binary input.

    5.10 t-tuple estimate¶

    The idea in plain words. Rather than looking at single values, we also look at pairs, triples and longer groups. If some group is much too common, its frequency implies a high per-sample probability. We take the worst such implied probability. It is like noticing a loaded die through its favourite pairs of rolls, not just its single numbers.

    Example 5.10: t-tuple estimate

    Using a cutoff of 3 for illustration and the \(L = 21\) samples

    \[S = (2, 2, 0, 1, 0, 2, 0, 1, 2, 1, 2, 0, 1, 2, 1, 0, 0, 1, 0, 0, 0),\]

    we get \(Q[1] = 9\), \(Q[2] = 4\), \(Q[3] = 3\). The values \(P_{max}[i]\) are 0.4286, 0.4472, 0.5405. So \(p_u = 0.8276\) and the estimate is 0.273 bits.

    The mathematics.

    \[P[i] = \frac{Q[i]}{L-i+1}, \qquad P_{max}[i] = P[i]^{1/i}, \qquad \hat{p}_{max} = \max_{1 \le i \le t} P_{max}[i]\]
    \[p_u = \min\!\left(1,\ \hat{p}_{max} + 2.576\sqrt{\frac{\hat{p}_{max}(1-\hat{p}_{max})}{L-1}}\right), \qquad H = -\log_2 p_u\]
    • \(t\) is the largest length whose most common tuple occurs at least 35 times.
    • \(Q[i]\) is the count of the most common \(i\)-tuple, with overlaps allowed.

    What it catches and misses. It catches repeated short patterns that single-value counts miss. It is limited to tuples common enough to count at least 35 times, which leaves longer patterns for the next estimator.

    5.11 Longest repeated substring (LRS) estimate¶

    The idea in plain words. This one picks up where the t-tuple estimate stops. For tuple lengths too rare to count well, we look at how often two positions match, a collision measure. It estimates collision entropy, which is an upper bound on min-entropy, so NIST uses it to complement the other estimates.

    Example 5.11: Longest repeated substring (LRS) estimate

    With the same \(S\) and the same illustrative cutoff of 3, \(u = 4\) and \(v = 5\). Then \(P_4 = 0.0131\) and \(P_5 = 0.0074\), so \(P_{max,4} = 0.3381\) and \(P_{max,5} = 0.3744\). So \(p_u = 0.6531\) and the estimate is 0.6146 bits.

    The mathematics.

    \[P_W = \frac{\sum_i \binom{C_i}{2}}{\binom{L-W+1}{2}}, \qquad P_{max,W} = P_W^{1/W}, \qquad \hat{p} = \max_{u \le W \le v} P_{max,W}\]
    \[p_u = \min\!\left(1,\ \hat{p} + 2.576\sqrt{\frac{\hat{p}(1-\hat{p})}{L-1}}\right), \qquad H = -\log_2 p_u\]
    • \(u\) is the smallest length whose most common tuple occurs fewer than 35 times.
    • \(v\) is the longest length that repeats at all. If \(v < u\) the estimate cannot be computed.
    • \(C_i\) is the number of occurrences of the \(i\)th distinct \(W\)-tuple.

    What it catches and misses. It handles tuple sizes too long for the t-tuple estimate, and so catches long repeats and replay. Because it measures collision rather than min-entropy, it can sit above the true min-entropy, and this is one reason the minimum across all estimates is taken.

    5.12 MultiMCW prediction estimate¶

    The idea in plain words. Here we stop counting and start guessing. Four simple predictors each guess the most common value in a recent window, and a scoreboard picks whichever has been right most often. If the guesses beat chance, the data is predictable. This suits sources whose favourite value drifts over time.

    Example 5.12: MultiMCW prediction estimate

    The standard's illustration uses \(S = (1, 2, 1, 0, 2, 1, 1, 2, 2, 0, 0, 0)\) with windows 3, 5, 7, 9. This gives correct \(= (0, 0, 0, 1, 0, 1, 0, 0, 1)\), so \(P_{global} = 0.3333\), \(P'_{global} = 0.7627\) and \(P_{local} = 0.036\). The estimate is \(-\log_2 0.7627 = 0.3908\) bits.

    The mathematics. All four prediction estimators share this ending.

    \[P_{global} = \frac{C}{N}, \qquad P'_{global} = \min\!\left(1,\ P_{global} + 2.576\sqrt{\frac{P_{global}(1-P_{global})}{N-1}}\right)\]
    \[0.99 = \frac{1 - P_{local}\,x}{(r + 1 - rx)\,q} \cdot \frac{1}{x^{N+1}}, \qquad x_j = 1 + q P_{local}^{\,r} x_{j-1}^{\,r+1}\]
    \[H = -\log_2 \max\!\left(P'_{global},\ P_{local},\ \frac{1}{k}\right)\]
    • \(C\) is the number of correct predictions out of \(N\). If \(C = 0\), \(P'_{global} = 1 - 0.01^{1/N}\).
    • \(r\) is one more than the longest run of correct predictions, \(q = 1 - P_{local}\), \(x = x_{10}\) and \(x_0 = 1\).
    • \(k\) is the alphabet size. Here the windows are \(w = 63, 255, 1023, 4095\) and \(N = L - 63\).

    What it catches and misses. It catches a most common value that shifts over time, and the local term catches bursts of predictability. A predictor can only prove structure it knows how to exploit, so a failure to predict is not proof of entropy.

    5.13 Lag prediction estimate¶

    The idea in plain words. There are 128 subpredictors, and each simply guesses "the next value equals the one \(d\) steps back". If the data has a rhythm of period \(d\), that subpredictor starts winning. It is like predicting that this week's quiz question will match the one from exactly a fortnight ago.

    Example 5.13: Lag prediction estimate

    The standard's illustration uses \(S = (2, 1, 3, 2, 1, 3, 1, 3, 1, 2)\) with \(D = 3\). This gives correct \(= (0, 0, 0, 1, 1, 0, 0, 0, 0)\), so \(P_{global} = 0.2222\), \(P'_{global} = 0.6008\) and \(P_{local} = 0.1167\). The estimate is 0.735 bits.

    The mathematics. The prediction at step \(i\) comes from the current winner \(d\):

    \[\mathrm{lag}_d = s_{i-d}, \qquad 1 \le d \le D, \qquad D = 128, \qquad N = L - 1\]
    • \(s_i\) is sample \(i\), and the winner is the subpredictor with the top score. When a subpredictor is correct and its score reaches or passes the winner's, it becomes the winner.
    • \(C\), \(r\), \(P'_{global}\), \(P_{local}\) and \(H\) follow the MultiMCW formulas above.

    What it catches and misses. It catches periodic sources with a period of up to 128 samples, such as interference from a clock. It sees only exact repeats at a fixed lag, so a period beyond 128 or a pattern that drifts in phase is missed.

    5.14 MultiMMC prediction estimate¶

    The idea in plain words. A Markov model with counting asks: after this recent context, which value usually came next? We run 16 of them, using contexts of length 1 to 16, and a scoreboard picks the best. Think of predictive text on a phone, trying short and long contexts at once.

    Example 5.14: MultiMMC prediction estimate

    The standard's illustration uses \(S = (2, 1, 3, 2, 1, 3, 1, 3, 1)\) with \(D = 3\). This gives correct \(= (0, 0, 1, 1, 0, 1, 0)\), so \(P_{global} = 0.4286\), \(P'_{global} = 0.9490\) and \(P_{local} = 0.1307\). The estimate is 0.0755 bits.

    The mathematics.

    \[\mathrm{subpredict}_d = \arg\max_{y}\ M_d\big[(s_{i-d}, \ldots, s_{i-1}),\ y\big], \qquad 1 \le d \le 16, \qquad N = L - 2\]
    • \(M_d[x, y]\) counts how often context \(x\) of length \(d\) was followed by \(y\), with ties going to the greatest \(y\).
    • Each model holds at most maxEntries \(= 100{,}000\) entries.
    • \(C\), \(r\), \(P'_{global}\), \(P_{local}\) and \(H\) follow the MultiMCW formulas above.

    What it catches and misses. It catches dependence on up to 16 previous samples, which suits non-binary sources with real memory. The entry limit means very rich context spaces fill up, and it cannot see dependence beyond 16 samples.

    5.15 LZ78Y prediction estimate¶

    The idea in plain words. This predictor builds a dictionary of the strings it has seen, as a compressor does, with each string recording what tends to follow it. To predict, it looks for the current context in the dictionary. If it has seen this story before, it bets on the same ending.

    Example 5.15: LZ78Y prediction estimate

    The standard's illustration uses \(S = (2, 1, 3, 2, 1, 3, 1, 3, 1, 2, 1, 3, 2)\) with \(B = 4\), so \(N = 8\). This gives correct \(= (0, 0, 1, 1, 0, 1, 1, 0)\), so \(P_{global} = 0.5\), \(P'_{global} = 0.9868\) and \(P_{local} = 0.1229\). The estimate is 0.0191 bits.

    The mathematics.

    \[\text{prediction} = \arg\max_{y}\ D[\mathrm{prev}][y] \text{ over the context lengths } j = B, \ldots, 1, \qquad B = 16, \qquad N = L - B - 1\]
    • \(D[\mathrm{prev}][y]\) counts how often string prev was followed by \(y\).
    • Each new sample updates every substring of the last \(B\) samples, and the dictionary stops growing at 65,536 entries.
    • Starting from the longest context, a shorter one replaces the current choice only if its count is higher. Ties between values go to the higher value.
    • \(C\), \(r\), \(P'_{global}\), \(P_{local}\) and \(H\) follow the MultiMCW formulas above.

    What it catches and misses. It catches repeated strings of up to 16 samples, whether or not they sit at a fixed lag. Once the dictionary fills, strings not already stored are never added, so structure that first appears late in a long stream can be missed.

    5.16 Restart tests¶

    The idea in plain words. A source might give a good estimate from one long run, yet start up the same way every time. An attacker who can reboot your device would love that. So we restart the source 1000 times, take 1000 samples each time, and check both across and along the results. It is like checking that a shuffled deck is not in the same order after every break.

    Example 5.16: Restart tests

    Suppose \(H_I = 8\), so \(p = 2^{-8}\). If the highest count in any row or column is 15, then \(\Pr(X \ge 15) = 1.44 \times 10^{-5}\), above the limit of \(5 \times 10^{-6}\), so the sanity check passes. A highest count of 16 gives \(3.41 \times 10^{-6}\) and fails.

    The mathematics.

    \[\Pr(X \ge X_{max}) = \sum_{j=X_{max}}^{1000} \binom{1000}{j} p^j (1-p)^{1000-j} < \alpha \implies \text{fail}, \qquad p = 2^{-H_I}, \quad \alpha = 0.000005\]
    \[H_r, H_c \text{ estimated on row and column data}, \qquad \min(H_r, H_c) < \frac{H_I}{2} \implies \text{fail}, \qquad H = \min(H_r, H_c, H_I)\]
    • \(X_{max}\) is the highest count of any value in any row or column of the \(1000 \times 1000\) matrix.
    • \(H_I\) is the initial estimate from earlier.
    • \(\alpha = 0.000005\) gives 0.01 overall across 2000 experiments.

    What it catches and misses. It catches correlated start-up behaviour, and it is unique in testing the source across restarts. It needs real restarts, so it cannot be run from a stored file, and it only tests the restart process you define, under normal conditions.

    5.17 Repetition count test (RCT)¶

    The idea in plain words. This is a smoke alarm, running all the time inside the device. If the same sample repeats too many times in a row, the source has probably stuck. It is cheap and quick, and NIST describes it as an update of the older stuck test from FIPS modules.

    Example 5.17: Repetition count test (RCT)

    With \(\alpha = 2^{-20}\) and \(H = 2\) bits per sample, \(C = 1 + \lceil 20/2 \rceil = 11\), the standard's example. A source assessed at 8 bits with \(C = 6\) gives a false alarm about once in \(10^{12}\) samples, as the standard notes.

    The mathematics.

    \[C = 1 + \left\lceil \frac{-\log_2 \alpha}{H} \right\rceil\]
    • \(H\) is the assessed min-entropy per sample, and \(\alpha\) is the accepted false-alarm probability.
    • The chance of \(C\) identical samples in a row is at most \(2^{-H(C-1)}\).
    • An error is raised when a sample repeats \(C\) or more times. NIST recommends \(\alpha\) between \(2^{-20}\) and \(2^{-40}\).

    How a laboratory sets \(H\). NIST tests against the developer's claimed \(H\), so the lab accepts one as the declared min-entropy. Without a claim it uses the sample's most common value estimate, because the fuller assessment collapses on a single stuck patch and would hide the fault under test. If \(H\) is so low that a cutoff cannot be reached, a measured value fails the test and a declared value skips it. The same applies to the APT below.

    What it catches and misses. It catches total failure, where the source gets stuck. NIST is frank that it is not very powerful. If that 8-bit source drops to 4 bits per sample, each sample matching the last with chance \(1/16\), it would still take about a million samples to notice.

    5.18 Adaptive proportion test (APT)¶

    The idea in plain words. This alarm watches for a subtler failure, where one value becomes too common without necessarily repeating in a row. Take a sample, then count how often it comes up in the next window. If the count hits a cutoff, the source has probably lost entropy. It is like spotting that one face of a die has started turning up too often.

    Example 5.18: Adaptive proportion test (APT)

    The standard's table for \(\alpha = 2^{-20}\) follows. We recomputed every entry and they all match.

    Binary, \(W = 1024\): \(H\) Cutoff \(C\) Non-binary, \(W = 512\): \(H\) Cutoff \(C\)
    0.2 941 0.5 410
    0.4 840 1 311
    0.6 748 2 177
    0.8 664 4 62
    1 589 8 13

    The mathematics.

    \[\Pr(B \ge C) \le \alpha, \qquad B \sim \mathrm{Binomial}\!\left(W, 2^{-H}\right), \qquad C = 1 + \mathrm{CRITBINOM}\!\left(W, 2^{-H}, 1 - \alpha\right)\]
    • \(W\) is the window size: 1024 for binary sources and 512 otherwise.
    • \(B\) counts how often the window's first sample occurs in the window, including itself.
    • CRITBINOM is the spreadsheet function giving the smallest count whose cumulative binomial probability reaches \(1 - \alpha\).

    For binary sources, a developer may also check that \(W - B\) stays below \(C\).

    What it catches and misses. It catches a large loss of entropy from a physical fault or a change in environment. It follows only the first value of each window, so it needs some windows to see the fault. Failures that keep all value frequencies normal, such as a predictable cycle, pass straight through.

    5.19 Summary¶

    • SP 800-90B estimates min-entropy per sample of a raw noise source, from at least \(10^6\) consecutive samples and a \(1000\times1000\) restart matrix. The result is the minimum over the estimators, which is deliberately cautious.
    • The IID track applies only if the samples are claimed i.i.d. and the permutation, chi-square and longest-repeated-substring tests find nothing; everything else follows the non-IID track with the most-common-value, collision, Markov, compression, t-tuple, LRS and four predictor estimators.
    • The predictor estimators (MultiMCW, Lag, MultiMMC and LZ78Y) turn guessing into entropy: if a predictor beats chance, the data is predictable. A failure to predict is not proof of entropy.
    • Restart tests check that a source does not start up the same way each time. RCT and APT are the continuous health tests: RCT catches a stuck source, APT catches one value becoming too common.
    • The estimators support an analysis of the source; they do not replace it. A cleverly deterministic source can score high, which is why a design rationale is required.

    5.20 Exercises¶

    1. Three values have probabilities 0.5, 0.25 and 0.25. Find the Shannon entropy and the min-entropy. Which does SP 800-90B use, and why?

      Answer

      Shannon: \(-0.5\log_20.5-2\times0.25\log_20.25=0.5+1=1.5\) bits. Min-entropy: \(-\log_20.5=1\) bit. SP 800-90B uses min-entropy, because security depends on the attacker's best single guess, which is the most likely value.

    2. Apply the most common value estimate to a sample of \(L=100\) values in which the most common value appears 30 times.

      Answer

      \(\hat p=0.30\). Then \(p_u=0.30+2.576\sqrt{0.30\times0.70/99}=0.30+2.576\times0.0461=0.4186\) and the estimate is \(-\log_2 0.4186=1.256\) bits per sample.

    3. Find the repetition count cutoff \(C=1+\lceil20/H\rceil\) for \(H=2\), \(H=4\) and \(H=8\) bits per sample at \(\alpha=2^{-20}\). What happens to the cutoff as \(H\) rises, and why?

      Answer

      \(H=2\): \(C=11\). \(H=4\): \(C=6\). \(H=8\): \(C=4\). As the source is assessed to have more entropy, a long run of identical samples becomes less plausible, so the cutoff falls: a run of 4 identical bytes from an 8-bit source is already very unlikely.

    4. Why does the most-common-value estimate alone overestimate the entropy of a stream that simply alternates 0, 1, 0, 1, ...?

      Answer

      The two values are equally common, so \(\hat p\) is close to 0.5 and the estimate is close to a full bit per sample. But the stream is completely predictable. The MCV estimate sees only frequencies and is blind to dependence, which is why the other estimators exist and why the final answer is the minimum over all of them.

    5. Why are restart tests needed, and why can they not be run from a stored file?

      Answer

      A source might give a good estimate from one long run yet start up the same way every time, which an attacker who can reboot the device would exploit. The restart tests restart the source 1000 times, take 1000 samples each time, and check the rows and columns of the resulting matrix. They need genuine restarts, so a stored file of one long run cannot supply them.
