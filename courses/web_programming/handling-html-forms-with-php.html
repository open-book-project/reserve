    Unit 3: Handling HTML Forms with PHP¶

    Forms are how a visitor talks to a web application. This unit shows how a form is written, how its values travel to the server by GET and by POST, how PHP receives them in the superglobal arrays, and how a script must treat them: validate them, escape them, and, where the application needs to remember a visitor from one request to the next, keep them in a session or a cookie.

    It corresponds to Unit 3 of the course, Handling HTML Forms with PHP, which is allotted 12 lecture hours, the second largest share of the course. Most of the working code in the later units is a form handler of the kind developed here.

    Learning outcomes

    • Write an HTML form whose fields actually reach PHP — and explain why the name attribute is the only one that matters for that.
    • Describe exactly what travels over the network for a GET and for a POST, and choose between them for a given job with a reason.
    • Read every kind of input — text, radio, checkbox groups, multi-selects, textareas, hidden fields — out of $_GET and $_POST without warnings.
    • Name the superglobals and say what each holds.
    • Validate on the server, report every error at once, and redisplay the form with the user's answers still in it.
    • Explain why client-side validation is not validation, and demonstrate an XSS hole and its fix.
    • Use header() for the post/redirect/get pattern, and sessions to remember a user between requests.

    3.1 A form is a parcel of named values¶

    The idea, first

    A form is a way for the browser to send you a small parcel of named values. That is all it is. The browser collects one value per named field, packs them into a request, and asks the server for a page — passing the parcel along. PHP unpacks it into an array. Everything else in this unit is detail about the packing.

    There are exactly two ways to pack the parcel. GET writes the values into the web address after a question mark, where they are visible in the address bar, saved in history, and short. POST puts them in the body of the request, where they are not visible in the address bar and can be as large as you like. That is the whole of "GET versus POST"; the rest of what people say about it follows from those two sentences.

    And one thing that is not detail at all: everything in that parcel is a lie until you check it. The browser is a program on someone else's computer. The maxlength you set, the required you added, the dropdown that only offered three choices — all of it can be edited or ignored before the request is sent. Client-side validation is a courtesy to honest users. Server-side validation is the only validation there is, which is why the course lists "validate server-side data" as an outcome of the course.

    3.2 Creating a form¶

    Attribute On Does
    name every input The key in $_POST. No name, no data — this is the single most common reason a field "does not arrive"
    action the form which page receives it. Empty or omitted means this same page
    method the form get (the default) or post
    value every input the starting value — and for radios and checkboxes, the value that gets sent
    id + <label for> accessibility clicking the label focuses the field. Nothing to do with PHP
    required, pattern, min inputs browser-side checks. Helpful, and not security
    enctype="multipart/form-data" the form needed only when uploading a file

    A query string does not need a form¶

    Any link can carry parameters. This is how "next page", "sort by marks" and "edit record 17" links work, and you will use it constantly in Unit 4.

    Listing 3.3. Links as parameters

    <?php
$students = [
    ["roll" => 2231045, "name" => "Zoya Khan",  "marks" => 82],
    ["roll" => 2231046, "name" => "Aman Verma", "marks" => 67],
    ["roll" => 2231047, "name" => "Riya Singh", "marks" => 91],
    ["roll" => 2231048, "name" => "Dev Kapoor", "marks" => 55],
];

$sort = $_GET["sort"] ?? "roll";
$dir  = $_GET["dir"]  ?? "asc";

// Never trust a parameter: check it against a list of what is allowed
$allowed = ["roll", "name", "marks"];
if (!in_array($sort, $allowed, true)) $sort = "roll";
$dir = $dir === "desc" ? "desc" : "asc";

usort($students, function ($a, $b) use ($sort, $dir) {
    $r = $a[$sort] <=> $b[$sort];
    return $dir === "desc" ? -$r : $r;
});

function link_for($col, $sort, $dir) {
    $next = ($col === $sort && $dir === "asc") ? "desc" : "asc";
    $arrow = $col === $sort ? ($dir === "asc" ? " &uarr;" : " &darr;") : "";
    return "<a href=\"index.php?sort=$col&amp;dir=$next\">" . ucfirst($col) . "$arrow</a>";
}
?>

<h3>Class list — click a heading to sort</h3>
<table>
  <tr>
    <th><?= link_for("roll",  $sort, $dir) ?></th>
    <th><?= link_for("name",  $sort, $dir) ?></th>
    <th><?= link_for("marks", $sort, $dir) ?></th>
  </tr>
<?php foreach ($students as $s): ?>
  <tr>
    <td><?= $s["roll"] ?></td>
    <td><?= htmlspecialchars($s["name"]) ?></td>
    <td><?= $s["marks"] ?></td>
  </tr>
<?php endforeach; ?>
</table>

<p style="color:#666">sorting by <b><?= htmlspecialchars($sort) ?></b>,
   <?= htmlspecialchars($dir) ?></p>

    GET versus POST¶

    GET POST
    Data travels in the URL, after ? the request body
    Visible in the address bar Yes No
    Saved in browser history / bookmarkable Yes No
    Appears in server logs and Referer headers Yes No
    Size limit ~2000 characters in practice (a browser and server limit, not a rule of HTTP) Effectively unlimited (post_max_size, 8 MB by default)
    Can send a file No Yes, with enctype="multipart/form-data"
    Cached by browsers and proxies Yes No
    Re-submitted on refresh Silently The browser asks first
    Read in PHP from $_GET $_POST
    Use it for Asking for something: search, filter, sort, page number, "show record 17" Changing something: register, log in, save, delete, upload
    Is it more secure? Neither is secure. POST merely keeps values out of the address bar and the logs; the body is just as readable to anyone watching the network. Only HTTPS makes a request private

    The rule of thumb: Safe and idempotent → GET. Otherwise → POST.

    A GET should be safe: repeating it changes nothing. If pressing refresh twice would place two orders, enrol a student twice, or delete two rows, the request had to be a POST. This is not a style preference — search engines and browsers pre-fetch GET links, and a "delete" link with a GET behind it has emptied more than one database.

    3.5 The PHP global variables¶

    A superglobal is an array PHP fills in for you before your script runs. They are visible everywhere — inside functions too, with no global declaration, which is what makes them "super".

    Superglobal Holds Filled from
    $_GET query-string parameters the text after ? in the address
    $_POST submitted form fields the request body
    $_REQUEST GET, POST and cookies merged convenient, and best avoided — you lose track of where a value came from
    $_SERVER information about the request and the server Apache and PHP
    $_SESSION values remembered between requests for one visitor the server, after session_start()
    $_COOKIE cookies the browser sent back the Cookie header
    $_FILES uploaded files a multipart POST
    $_ENV environment variables the operating system
    $GLOBALS every global variable, by name PHP itself

    "QUERY_STRING"   => "everything after the ? in the address",
    "REQUEST_URI"    => "path and query together",
    "HTTP_HOST"      => "the host the browser asked for",
    "REMOTE_ADDR"    => "the visitor's IP address",
    "DOCUMENT_ROOT"  => "where htdocs lives on disk",

    The self-processing form¶

    Most real forms post back to the page they came from: one file holds both the form and the code that handles it. That is what makes it possible to redisplay the form with the errors marked and the answers still in place.

    Listing 3.6. One file, both jobs

    <?php
$message = "";

// Has this page been reached by a submission, or by someone just opening it?
if ($_SERVER["REQUEST_METHOD"] === "POST") {
    $a = (float) ($_POST["a"] ?? 0);
    $b = (float) ($_POST["b"] ?? 0);
    $message = "$a + $b = " . ($a + $b);
}
?>

<h3>Add two numbers</h3>

<?php if ($message): ?>
  <p style="background:#eef8f2;border-left:5px solid #1a7f4b;padding:8px">
    <b><?= htmlspecialchars($message) ?></b></p>
<?php endif; ?>

<form action="" method="post">
  <p><label for="a">First</label>
     <input type="text" id="a" name="a" value="<?= htmlspecialchars($_POST["a"] ?? "") ?>"></p>
  <p><label for="b">Second</label>
     <input type="text" id="b" name="b" value="<?= htmlspecialchars($_POST["b"] ?? "") ?>"></p>
  <p><button type="submit">Evaluate</button></p>
</form>

    Output sent to the browser:

    The same file draws the form and handles it, and the if at the top decides which. Notice that the form's action is empty, which is the simplest and safest way to post to the same page.

    action='', $_SERVER['PHP_SELF'], or nothing

    All three post to the same page. action="" is the simplest and is completely safe. If you use PHP_SELF — as many textbooks do — you must escape it: action="<?= htmlspecialchars($_SERVER['PHP_SELF']) ?>", because on some server setups an attacker can append markup to the path and get it echoed into your page. action="" avoids the whole question.

    3.6 Every kind of input, and how it arrives¶

    Text fields are easy. The ones worth practising are the ones that can send nothing at all, or send several values at once.

    Listing 3.7. The full form — one of everything

    index.php

    The tools¶

    Check How
    Present at all isset($_POST["x"])
    Not blank trim($_POST["x"] ?? "") !== "" — not empty(), which rejects "0"
    Letters and spaces only preg_match('/^[A-Za-z ]+$/', $name)
    Exactly n digits preg_match('/^\d{7}$/', $roll)
    A number in a range is_numeric($m) && $m >= 0 && $m <= 100
    An email address filter_var($e, FILTER_VALIDATE_EMAIL)
    An integer filter_var($n, FILTER_VALIDATE_INT) — returns the int, or false
    A URL filter_var($u, FILTER_VALIDATE_URL)
    One of a fixed set in_array($v, ["CS Hon", "BA Eco"], true)
    Two fields match $p1 === $p2 — with ===
    A date checkdate($m, $d, $y), or compare with strtotime()

    filter_var returns the value, not true

    filter_var("0", FILTER_VALIDATE_INT) returns the integer 0, which is falsy — so if (filter_var(...)) rejects a legitimate zero. Test it with !== false.

    The sticky, self-validating form¶

    This is the pattern to learn by heart. One file; validate on POST; if anything is wrong, fall through and redraw the form with the messages beside the fields and the user's answers still in place. Losing a user's typing because of one bad field is the fastest way to lose the user.

           "course" => "", "gender" => "", "subjects" => []];

if ($_SERVER["REQUEST_METHOD"] === "POST") {

    // 1. collect and clean
    foreach ($fields as $k => $default) {
        if (is_array($default)) $fields[$k] = $_POST[$k] ?? [];
        else                    $fields[$k] = trim($_POST[$k] ?? "");
    }

    // 2. check, collecting every problem rather than stopping at the first
    if ($fields["sname"] === "")                                  $errors["sname"]  = "Name is required";
    elseif (!preg_match('/^[A-Za-z ]{3,50}$/', $fields["sname"])) $errors["sname"]  = "3-50 letters and spaces only";

    if (!preg_match('/^\d{7}$/', $fields["rollno"]))              $errors["rollno"] = "Roll number must be exactly 7 digits";

    if (!filter_var($fields["email"], FILTER_VALIDATE_EMAIL))     $errors["email"]  = "That is not a valid email address";

    3.9 Uploading a file¶

    A file is the one kind of input that does not arrive in $_POST. It needs a different encoding on the form, and it lands in its own superglobal.

    Requirement Why
    enctype="multipart/form-data" on the form The default encoding cannot carry raw bytes. Forget this and $_FILES is simply empty — the single commonest upload bug
    method="post" A GET has no body to put the file in
    <input type="file" name="photo"> name becomes the key in $_FILES, as always

    What $_FILES holds¶

    Key Is Trust it?
    name the file name on the visitor's machine No. It is a string the browser sent; it can contain anything
    type the MIME type the browser claimed No. Anyone can claim image/jpeg
    tmp_name where PHP parked it on the server Yes — this is PHP's own value, and the file is deleted when the script ends
    size bytes actually received Yes
    error 0 = UPLOAD_ERR_OK; other codes explain the failure Yes — check this first, always

    Listing 3.11. An upload handler, with every check

    <?php
// The form that produced this had enctype="multipart/form-data".

if (!isset($_FILES["photo"])) {
    exit("No file field was submitted at all.\n");
}

$file    = $_FILES["photo"];
$maxSize = 2 * 1024 * 1024;                    // 2 MB
$allowed = ["jpg", "jpeg", "png", "gif"];

echo "What arrived:\n";
print_r($file);
echo "\n";

// 1. the error code comes first — everything else is meaningless without it
if ($file["error"] !== UPLOAD_ERR_OK) {
    $why = [
        UPLOAD_ERR_INI_SIZE  => "larger than upload_max_filesize in php.ini",
        UPLOAD_ERR_FORM_SIZE => "larger than the form's MAX_FILE_SIZE",
        UPLOAD_ERR_PARTIAL   => "only partly uploaded",
        UPLOAD_ERR_NO_FILE   => "no file was chosen",
    ];
    exit("Upload failed: " . ($why[$file["error"]] ?? "error " . $file["error"]) . "\n");
}

// 2. size — the browser's own limit is advisory, so check it here
if ($file["size"] > $maxSize) {
    exit("Too large: " . round($file["size"] / 1024) . " KB, limit 2048 KB\n");
}

// 3. the extension, taken from the name and lower-cased
$ext = strtolower(pathinfo($file["name"], PATHINFO_EXTENSION));
if (!in_array($ext, $allowed, true)) {
    exit("Type '$ext' is not allowed. Permitted: " . implode(", ", $allowed) . "\n");
}

// 4. was it really uploaded by PHP, or is someone naming a system file?
if (!is_uploaded_file($file["tmp_name"])) {
    exit("That is not an uploaded file.\n");
}

// 5. invent our own name. NEVER reuse the one the browser sent.
$newName = "photo_" . date("Ymd") . "_" . uniqid() . "." . $ext;
$target  = "uploads/" . $newName;

if (move_uploaded_file($file["tmp_name"], $target)) {
    echo "Accepted.\n";
    echo "  stored as : $target\n";
    echo "  size      : " . round($file["size"] / 1024) . " KB\n";
    echo "  original  : " . htmlspecialchars($file["name"]) . "  (kept only for display)\n";
} else {
    echo "Could not move the file — check that uploads/ exists and is writable.\n";
}

    3.11 Solved problems¶

    Example 3.1: Why does my checkbox never arrive?

    Problem. A student writes <input type="checkbox" name="agree"> and then if ($_POST["agree"] == "on") { … }. Ticked, it works. Unticked, the page shows a warning. Explain and fix.

    Step 1 — what the browser sends

    A ticked checkbox sends its value, defaulting to the string "on" when no value attribute is given. An unticked checkbox sends nothing whatsoever — there is no empty value, no "off"; the key simply does not exist in $_POST.

    Step 2 — why the warning appears

    $_POST["agree"] on a missing key is "Warning: Undefined array key", and the expression evaluates to null. The comparison then quietly fails, so the logic is right by accident and the log fills with warnings.

    Step 3 — the fix

    Ask whether it exists, not what it equals: if (isset($_POST["agree"])). Give the box an explicit value if you need to distinguish several boxes.

    Step 4 — the group version

    For several checkboxes with the same purpose, name them subjects[] and read $_POST["subjects"] ?? []. The ?? [] means the foreach that follows works even when nothing was ticked.

    Answer. isset($_POST["agree"]) for one box; $_POST["subjects"] ?? [] for a group

    Example 3.2: The form loses everything on one mistake

    Problem. A registration form with eight fields rejects a bad email and redraws itself — empty. Users abandon it. What is wrong, and what does the fix look like?

    Step 1 — why it happens

    The form is redrawn from the original HTML, in which every value="" is blank. Nothing puts the submitted values back.

    Step 2 — the fix for text fields

    value="<?= htmlspecialchars($_POST['sname'] ?? '') ?>". The ?? covers the first visit, when there is no POST at all; the htmlspecialchars stops a quote in the value from ending the attribute and letting markup in.

    Step 3 — the other controls

    They each need their own word rather than a value: selected on the matching <option>, checked on the matching radio, and in_array($s, $chosen) to decide checked for each box in a group. The registration lab above shows all three.

    Step 4 — why escaping is not optional here

    Without it, a name containing a double quote — or a deliberately crafted " onmouseover="… — breaks straight out of the attribute. A sticky form that is not escaped is an XSS hole that the site's own users fill in.

    Answer. Re-echo every submitted value, escaped, and add selected / checked for the rest

    Example 3.3: 'Headers already sent'

    Problem. A login page works, but header("Location: home.php") produces Warning: Cannot modify header information — headers already sent by (output started at /var/www/config.php:12). Diagnose it.

    Step 1 — read the message properly

    It names the file and line where output began: config.php line 12. That is the culprit, not the line with header() on it.

    Step 2 — what counts as output

    Anything at all: an echo, a stray character, a blank line before <?php, a newline after ?>, or a byte-order mark that an editor saved at the top of the file. Once a single byte has gone, the headers have been flushed and cannot change.

    Step 3 — the fix

    Delete the whitespace, and — the habit that prevents it for good — leave off the closing ?> in any file that contains only PHP. Then there is nothing after it to leak.

    Step 4 — the same cause elsewhere

    The identical warning from session_start() and setcookie() has the identical cause, because all three send headers.

    Answer. Remove output before the header — usually a newline after ?> in an included file

    Example 3.4: Two buttons on one form

    Problem. A form needs "Save" and "Delete" buttons that submit to the same handler. How does the handler tell which was pressed?

    Step 1 — a submit button is a field

    Give each button the same name and a different value: <button name="action" value="save"> and value="delete". Only the button actually pressed is submitted, so $_POST["action"] holds one of the two.

    Step 2 — branch on it, defensively

    switch ($_POST["action"] ?? "") with a default that rejects anything unexpected. The value comes from the browser, so "delete_everything" is a request someone can make.

    Step 3 — the trap with <button>

    <button>Save</button> with no value sends an empty string in most browsers — the text between the tags is not the value. Always set value explicitly.

    Answer. Same name, different value, then branch on $_POST["action"]

    3.12 Common mistakes to avoid¶

    • Do not omit the name attribute. Without it the field is not submitted at all — no name, no data.
    • Do not read a checkbox with ==. Use isset(), and ?? [] for a name[] group.
    • Do not forget the [] on a multiple select or a checkbox group. Without it PHP keeps only the last value.
    • Do not trust required, pattern, maxlength or a dropdown's list of options. All of them live in the browser, and the browser belongs to the user.
    • Do not echo user input without htmlspecialchars(), including inside value="" attributes on a sticky form.
    • Do not output anything before session_start(), setcookie() or header() — not even a newline after ?>.
    • Do not leave out exit; after a redirect.
    • Do not use a GET for anything that changes data. Browsers and crawlers follow links on their own.
    • Do not use empty() to mean "was it filled in". The strings "0" and "0.0" are legitimate answers, and empty("0") is true.
    • Do not put a password in a GET form. It ends up in the address bar, the history and the server's access log.
    • Do not forget enctype="multipart/form-data" on a form with a file input — without it $_FILES is empty and nothing says why.
    • Do not save an uploaded file under the name the browser supplied, and do not believe the type it claims.
    • Do not assume $_POST["marks"] is a number. It is the string "82"; cast it when you need arithmetic.

    • You can answer "is POST more secure?" correctly: no, it merely keeps values out of the address bar, the history and the logs, and only HTTPS makes a request private.
    • You can name the superglobals and use the four that matter, and you know $_SERVER["REQUEST_METHOD"] is the test that makes a self-processing form possible.
    • You can read every kind of control, including the two that catch everyone: an unticked checkbox sends nothing, and a group of them needs [] in the name and ?? [] in the handler.
    • You can write the standard form shape — check the method, collect and trim, validate into an $errors array, then act or redraw — and make the redrawn form sticky for text fields, selects, radios and checkbox groups alike.

    Quick check — GET and POST¶

    Exercise 3.1. A form has <input type="text" value="Zoya"> with no name attribute. After submitting, what is in $_POST?

    • (a) Nothing from that field at all
    • (b) $_POST[0] = "Zoya"
    • (c) $_POST["text"] = "Zoya"
    • (d) $_POST["Zoya"] = ""
    Answer

    The answer is (a).

    • (a) Correct. Right. The browser only sends fields that have a name — the name is the key. This is the number one cause of 'my value does not arrive'.
    • (b) There is no positional fallback; unnamed fields are simply not submitted.
    • (c) The type is not used as a key.
    • (d) The value never becomes the key.

    Exercise 3.2. Which of these should be a POST?

    • (a) A link that deletes a student record
    • (b) A search box on the library catalogue
    • (c) A link to page 3 of the results
    • (d) A dropdown that changes the sort order
    Answer

    The answer is (a).

    • (a) Correct. Correct. Anything that changes data must be a POST — a GET can be pre-fetched by a browser or crawler, and refresh repeats it silently.
    • (b) A search is safe and repeatable, and a GET makes the results shareable and bookmarkable.
    • (c) Pagination is a GET, so page 3 has its own address.
    • (d) Sorting changes nothing on the server, so GET is right and the sorted view gets its own URL.

    Exercise 3.3. Is POST more secure than GET?

    • (a) No — but it keeps values out of the address bar, history and server logs
    • (b) Yes — POST data is encrypted
    • (c) Yes — POST data cannot be intercepted
    • (d) No — they are identical in every way
    Answer

    The answer is (a).

    • (a) Correct. Exactly the right answer, and the one examiners look for. Both send data in plain text unless the connection is HTTPS.
    • (b) Nothing about POST encrypts anything. Only TLS does that.
    • (c) The body is as readable as the URL to anyone on the network path.
    • (d) They differ in visibility, size, caching and refresh behaviour; those differences matter, they are just not encryption.

    Exercise 3.4. A page is opened directly, with no form behind it. What does echo $_POST["name"]; do in PHP 8?

    • (a) Prints nothing, and emits Warning: Undefined array key "name"
    • (b) Prints nothing, silently
    • (c) Throws a fatal error and stops
    • (d) Prints NULL
    Answer

    The answer is (a).

    • (a) Correct. Correct — it is a warning, not a fatal error, so the page continues. Guard it with isset() or ?? to keep the log clean.
    • (b) PHP 8 warns about undefined array keys; PHP 5 issued a quieter notice, which is why old code gets away with it.
    • (c) Only undefined functions and similar are fatal.
    • (d) The expression is null and echoing null prints an empty string.

    Exercise 3.14. Why must exit; follow header("Location: next.php");?

    Exercise 3.23. Explain why <input type="hidden" name="price" value="500"> is not a safe way to carry a price to the payment page. What should carry it instead?

    Answer

    A hidden field is hidden only from the page as displayed. The user can see it with "View source", change it with the browser's developer tools, or send a request with any value at all using a tool such as curl. A user could therefore pay 1 instead of 500.

    Exercise 3.29. (2 marks) What are superglobals? Name any four.

    Answer

    Built-in arrays that PHP fills in before your script runs and that are visible in every scope — inside functions too — without a global declaration.

    Exercise 3.30. (2 marks) Which attribute of a form field determines the key in $_POST?

    Answer

    name. <input name="rollno"> arrives as $_POST["rollno"]. A field with no name attribute is not submitted at all — neither id nor value substitutes for it, and this is the commonest reason a value "does not arrive".

    Exercise 3.31. (2 marks) How do you check whether a checkbox was ticked?

    Answer

    With isset(). An unticked checkbox sends nothing at all — the key is absent from $_POST, rather than being empty or "off".

    Exercise 3.32. (2 marks) What is $_SERVER["REQUEST_METHOD"] used for?

    Answer

    To tell a first visit from a submission, which is what makes a self-processing form — one file that both draws the form and handles it — possible.

    if ($_SERVER["REQUEST_METHOD"] === "POST") {
    // handle the submission
} else {
    // draw the empty form
}

    Exercise 3.33. (2 marks) Why must session_start() appear before any output?

    Answer

    Because it sends a Set-Cookie HTTP header carrying the session id, and headers must precede the body. Once a single byte of output has gone — even a blank line before <?php or a newline after ?> in an included file — the headers are already sent and PHP warns "Cannot modify header information". The same applies to header() and setcookie().

    Exercise 3.36. (5 marks) What is form validation? Differentiate client-side and server-side validation.

    Answer

    Validation is checking that submitted data is acceptable — present, the right shape, within range — before acting on it.

    Client-side Server-side

    Exercise 3.37. (5 marks) What is a sticky form, and how do you make one?

    Answer

    A form that redisplays the values the user already typed when validation fails, instead of clearing itself. Without it, one bad field costs the user the whole form.

    Text fields — echo the submitted value back into value, escaped:

    <input type="text" name="sname"
       value="<?= htmlspecialchars($_POST['sname'] ?? '', ENT_QUOTES) ?>">

    Select — mark the matching option selected:

    <option value="UG" <?= ($_POST['course'] ?? '') === 'UG' ? 'selected' : '' ?>>UG</option>

    Radio and checkbox — mark them checked, using in_array() for a group.

    The htmlspecialchars is not optional: without it a quotation mark in the value escapes the attribute, turning your own sticky form into an XSS hole.

        $errors = [];
    if (!preg_match('/^[A-Za-z ]{3,50}$/', $f["sname"]))  $errors["sname"]  = "3-50 letters";
    if (!preg_match('/^\d{7}$/', $f["rollno"]))           $errors["rollno"] = "7 digits";
    if (!filter_var($f["email"], FILTER_VALIDATE_EMAIL))  $errors["email"]  = "Invalid email";
    if (!in_array($f["gender"], ["F","M","O"], true))     $errors["gender"] = "Choose one";
    if (count($f["subjects"]) < 2)                        $errors["subjects"] = "Pick two";
}

    4. Act or redraw — if $errors is empty, save (Unit 4) and redirect; otherwise redraw the form with the messages beside the fields and the values still in place.

    Points to mention for the remaining marks: every value arrives as a string; an unticked checkbox sends nothing; validation must happen on the server because the browser can be bypassed; and every echoed value needs htmlspecialchars().

    Exercise 3.39. (10 marks) Explain file uploading in PHP. What does $_FILES contain, and what checks must a handler perform?

    Answer

    The form needs two things — POST, and the multipart encoding:

    <form action="upload.php" method="post" enctype="multipart/form-data">
  <input type="file" name="photo">
  <button type="submit">Upload</button>
</form>

    Without enctype="multipart/form-data", $_FILES is empty and nothing explains why.

    $_FILES["photo"] holds five keys: name (the visitor's file name), type (the MIME type the browser claimed), tmp_name (where PHP parked it), size (bytes), and error (0 = UPLOAD_ERR_OK). Only tmp_name, size and error are trustworthy; the other two come from the browser.

    The handler:

    $f = $_FILES["photo"];

if ($f["error"] !== UPLOAD_ERR_OK)        exit("Upload failed");
if ($f["size"] > 2*1024*1024)             exit("Too large");

$ext = strtolower(pathinfo($f["name"], PATHINFO_EXTENSION));
if (!in_array($ext, ["jpg","jpeg","png"], true)) exit("Type not allowed");
if (!is_uploaded_file($f["tmp_name"]))    exit("Not an uploaded file");

$target = "uploads/" . uniqid("img_") . "." . $ext;   // OUR name, not theirs
move_uploaded_file($f["tmp_name"], $target);

    Three security points worth the marks: never store the file under the name the browser supplied (../../index.php is a valid string); never put uploads in a folder the server will execute; and never trust the claimed type. The temporary file is deleted automatically when the script ends, so it must be moved during that request.
